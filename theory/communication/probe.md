# Probe

agent 识别讨论难以补足的细节，主动提出合适的实践

## Fidelity

先明确要回答的问题，以及哪些实际表现影响理解或判断，再决定实现形状：脚本、可交互 demo、真实链路或多方案比较

保真度按维度分配：决定结论的维度足够真实，其余工程完备性尽量简化。要测量的行为必须真实发生

> 例：比较 PDF 解析方案 A、B、C 的总时间，可以省去 UI、部署和配置体系，但需要可比较的输入、资源条件与计时范围，并核对解析工作量和结果质量

> 例：判断一个 UI 方案时，影响感受的信息、布局和交互要足够真实，后端可以用假数据

## Evidence

呈现实际观察、对比结果、适用条件与尚未验证的部分，让 user 看清它回答了什么、能支持到哪里。指标为当前问题服务。测量要先能失败，否则不算证据，见 [Validity 的 Evidence](../primitive/validity.md#evidence)

Probe 提供依据，取舍回到[决定](decision.md)

代码、跑通的关键路径、有效用法、测试样本、测量方法、基线与失效条件，都可以指导正式实现。复用多少，在正式实现时选择

## Completion

**回答了约定的问题即完成。后续用途结束即退役**

- A、B、C 都不满足条件，但依据已足以回答比较问题，这次 Probe 完成。寻找 D 是新的决定
- 只为对齐一个想法，取得依据后可以直接退役
- UI 已选定，Probe 仍供正式实现对照，保留到真实版本完成
- 测量脚本、样本或基线仍有正式用途时，归入对应的测试或依据

Probe 起的服务、脚本与数据都是 [Byproduct](../agency/effect.md#kinds)：产生时登记，退役时先承接结论与仍有用途的材料，其余按 [Effect 的 Ending](../agency/effect.md#ending) 收回
