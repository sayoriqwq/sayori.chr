# Worktree

## Isolation

独立开发任务在隔离的工作树与任务分支上推进，与主干检出目录分离。每棵工作树在所属工作区的环境契约中登记路径、分支、用途、负责人与退出条件，使物理工作树始终处于职责树视野之内

物理工作树登记只说明目录存在，谁仍在使用由真实消费方核实

## Retirement

产品仓分支与工作树满足以下两个条件时进入清退：提交已完整合入目标主干，且核实不存在仍在依赖该工作树的活跃消费方。清退节奏与 [Task 的 Lifetime](../delivery/task.md#lifetime) 联动：

- **一次性 Task**：激进收口，对应分支合入并确认无消费方后立即移除工作树与临时分支，Task 收口时一并移除工作目录
- **常驻 Task**：保留长期职责与持续上下文，阶段性成果持续合并并回收单次开发副产物，直至 user 明确下达清退时彻底撤除工作树、分支与任务目录

> 例：缺少统一的清退时机约定会导致已合入工作树长期滞留磁盘，并使旧草稿分支在后续核查中被误判为活跃改动，见[工作区工程卫生规则缺位](../../cases/git-hygiene-gap.md)

## Audit

执行工作树与工程资源清退时，依次完成以下四步核查：

1. 核查工作树的独有提交、未提交文件与忽略文件，确认尚具价值的独有产出已转移至正式归属位置
2. 核查实际执行目录与写入出口是否存在由探针、测试替身或临时脚本留下的范围外写入
3. 核查关联服务、端口与共享资源的真实消费方，仅停止专有资源并完整保护共享依赖
4. 分别核实保留价值、正式归属与最终处置三项判断，在有效批准内同时清退工作树、已合入分支与临时材料，并回到环境回读确认实际状态

> 例：离线验证探针因缺失路径配置将二十四个模拟文件写入工作区根目录，仅检查已登记工作树与任务目录导致范围外残留被漏检，见[探针在工作目录留范围外写入](../../cases/test-output-outside-task.md)

> 例：确认待清理目录具有保留价值并指派保管人后便宣告完成，导致历史材料滞留现用配置目录且已合入分支仍未删除，见[保留材料误作完成处置](../../cases/preservation-is-not-disposition.md)
