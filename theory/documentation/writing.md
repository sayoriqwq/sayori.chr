# Writing

两条评判标准贯穿全页：

- **美观**：视觉上平衡，简洁优雅
- **可读性**：信息有层次，节省注意力，重点一眼可见

按读者的特定要求见 [Audience](audience/index.md)

## Statement

正文写本模块的对象、关系与依据，用正面陈述。与相邻模块的分界只在需要分界的入口写一次，例如领域 index 的 Scope

本页的核心主张写在[断言](../primitive/assertion.md#use)，正文从它的理由与条件展开

建设过程、进度与"本轮"一类措辞由 Git 历史承载，正文只写理论本身

## Tone

文档按人写给人读的方式来写，agent 读的部分也一样：

- **完整的句子**：主语、动作、对象写全，读起来像正常说话
- **日常说法**：用自然的中文表达，少用抽象名词化的造词，例如用"负责人"，不造"承担者""承担方式"
- **连贯**：段落之间有承接，结构化形式服务于阅读，正文保留叙述的连贯

## Naming

目录与文件用一个表意清晰的 leading word，表意不足时用 a-b 形式的简单组合，例如 `special-filenames.md`

一个名称承载一个职责。需要用 and 连接两个词才能命名时，说明职责尚未辨明，先拆分对象，再分别命名。需要更长的名称时，检查层级设计

## Forms

内容优先用结构化的 Markdown 形式组织：

| Form | Use |
| --- | --- |
| H2 标题 | 页内各节，英文，作锚点 |
| 列表 | 并列事项 |
| 粗体标签列表 | 名词加说明，或一个分支条件下各情形的处置，写作 `- **标签**：说明` |
| 编号列表 | 真正有先后的步骤 |
| 表格 | 同类事物在两个以上维度上对比 |
| 引用块 | [Example](#examples)，写作 `> 例：` |
| 行内代码 | 文件名、字段、取值等标识 |
| Mermaid | 关系或流程 |

- 一段只承担一个重点，保持在两三行以内。超过这个长度或包含并列项时，转成上表中的结构化形式
- 有分支时，先写出分支条件，再用粗体标签列表分述各情形。分支不编进编号步骤
- 一页需要 H3 时，先考虑是否该拆页
- 列表嵌套保持在两层以内，更深的层次放进标题或表格
- 表格的表头统一用一种语言，中文或英文均可
- 表格单元格写成短语
- HTML 与脚注不用

重要主张与其理由、条件保持邻近。代码与需要忠实保留的原文保持原样

## Examples

Example 把规则落到一个具体场景上，让读者看到规则实际怎样起作用。规则读完仍拿不准怎么用时，加一个 Example

- **形式**：引用块，以"例："开头，和规则在视觉上分开。一块一个场景，需要列举时在块内用列表
- **位置**：紧跟在它说明的规则后面
- **场景**：写具体的对象和动作，例如"在测试集群部署一个验证用的 pod"，读者能在自己的经历里认出它

> 例：在测试集群部署一个验证用的 pod。它是 Byproduct，也留在共享环境，部署前需要批准

Example 优先取自真实经历。取自一条 [Case](../evolution/case.md) 时，在块末附上链接，读者能回到原始记录。这样理论里的规则能追溯到让它成立的经历，Case 也有了被理论吸收的去处

Example 与 Case 是两件事：Example 是正文里说明规则的场景，Case 是进化中一次偏差的原始记录。一个 Case 可以被引作 Example，构造的 Example 不需要对应 Case

## Punctuation

中文标点服务于版面的干净：

- **段尾、列表项、表格单元格、断言与 description**：结尾不加句号
- **段内两句之间**：正常使用句号
- **分号**：不用。分号连起来的多项内容，按关系拆成列表、表格或独立的句子

## Claims

结论先行，再围绕它组织解释、依据与补充。主张、理由与成立条件写在一起

信息的 Form 按[效力](../primitive/validity.md#form)标明：Inference 标明是推断，未知直接说明

## Language

中英按用途分工：

- **正文用中文**：日常交互与文档正文以中文为主。常见英文单词与技术词汇直接使用，user 阅读无负担
- **难译的词用英文**：没有贴切中文的词直接用英文，例如 agent、token，不硬译
- **控制词用英文**：建模的概念及其取值，例如 Handoff 的 Delegate、Effect 的 Byproduct，用英文 leading word。词表同样以英文为主
- **可链接、可查询的标识用英文**：各级标题（作为 `#` 锚点）、frontmatter 的键与值、文件名、目录名。标题只写英文，中文说明放在正文

英文风格：

- **标识**：小写与连字符，例如 `special-filenames.md`、`validity: candidate`
- **建模的概念**：首字母大写，例如 Model、Effect、Handoff

leading word 是模型已经理解的紧凑词语，在全文中锚定同一个概念或行为。优先选现成的词，例如 Byproduct、Closeout

改标题时核对指向该锚点的链接

## Pruning

每个意思只有一处权威位置，其他地方引用它。同一概念的定义、规则与例外放在同一标题下

逐句检查：一句话删去后读者的理解或行为不变，就删去整句

## Change

修改一个模块时，从整体含义出发：先理解全文的结构与重点，再决定新内容归入哪一节、哪些段落一起改写。修订后全文读起来仍是一个整体

- **补充与修正**：归入现有结构，改写相应段落，断言保持不变
- **职责改变**：重审断言、description、上层路由、模块边界与相关引用
- **新增层级**：新增目录、分类或条目前，按 [Organization 的 Hierarchy](organization.md#hierarchy) 确定它在哪一层

追加式写作只用于日志类记录，例如 Decision Log、Case 与 Effect 登记。它们按时间追加，原条保持原样

阅读体验是检验标准：

- **频繁跳转**：理解同一问题需要频繁跳转时，聚合
- **相互干扰**：无关内容干扰理解时，拆分
