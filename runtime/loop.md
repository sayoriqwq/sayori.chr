# Loop

## Steps

[进化的 Loop](../theory/evolution/index.md#loop)在 sayori 中按六步运转：

1. **记录**：任何节点或 user 在发生处工作区的事件存储写入 Case，机制同时把缺报、长期未解待决项与意外 Effect 作为候选提供
2. **整理**：建设区负责维护 runtime 的 Mate 攒够一批或到周期时按 [Revision](#revision) 定位缺口，写成修订提议并预先写下[检验问题](../theory/evolution/evaluation.md#question)
3. **决定**：user 在决定日志逐份拍板，写明证据、修改层级、改法与有效判据
4. **修订**：维护 Mate 或其派出的 Sailor 在缺口所在层的独立分支实施修改，理论按本仓规则修订，设计页经候审状态审定，实现完成边界验证
5. **采用**：维护者经 user 批准后将改动合入主干并构建生效唯一共享分发入口，发布说明引用对应 Case，各工作区按需执行迁移并逐项撤除已接管的旧义务
6. **检验**：维护 Mate 对照原场景、相邻场景与正常行为核验效果，并在 Case 追加已验证或已复发记录

一圈集中处理这一圈暴露的明确缺口，每个改动各配独立检验问题。证据尚不足的条目留待后续观察。消费工作区的 Firstmate 负责记录 Case 与配合迁移检验，共享底座的整理与修订归属建设区

## Case

Case 按用途分为运行期原始记录与精选案例库两层：

| 层级 | 位置 | 准入与用途 |
| --- | --- | --- |
| 运行期原始记录 | 发生处工作区的事件存储 | 全量只追加记录日常偏差，服务当圈整理、状态折叠与复发追踪 |
| 精选案例库 | 本仓 [cases/](../cases/index.md) | 仅收录已被理论或设计正式吸收的典型偏差，脱敏并按预期、实际、证据与归因整理，供规则正文以链接直接回溯 |

每条 Case 遵循[记录的 Contracts](records.md#contracts)：拆分预期、实际与证据入口，缺失项显式留空。直接观察标为 Fact，原因假设标为 Inference，按只追加事件折叠生命周期

## Revision

按[进化的 Revision](../theory/evolution/index.md#revision)定位缺口，并区分设计层与工程层：

| 缺口 | 改法 |
| --- | --- |
| 理论 | 修改理论真源，沿出处复核受影响的设计页与派生物，必要时将支撑该规则的典型 Case 沉淀进精选案例库 |
| 设计 | 修改协作层或工程层设计页，重大变更退回候审状态待 user 确认 |
| 派生 | 修改协作层实现的机制代码或外部化内容文件 |
| 取得 | 规则已具备时调整进入上下文的方式，例如说明文案、加载顺序或唤醒条件 |
| 工程 | 修改工程层的工作区基座规范或通用工程 Skill |
| 环境 | 仅修改该工作区自身的配置、路由或特有规则 |

- **退场**：新机制接管某项旧人工规则后，在采用回执中逐项写明被替代的旧条款、仍保留的职责与回退条件，使新旧义务清晰交替
- **减法**：长期无 Case 且移除后行为保持稳定的规则，按[检验的 Value](../theory/evolution/evaluation.md#value)清理

## Provenance

- **内容**：协作层的外部化内容文件在入口元数据中写明对应的理论页、设计页与参考提交
- **独立包**：具备独立分发身份的工程 Skill 保持产物自包含，其理论出处集中登记于[工程 Skill 的 Registry](../dev/skills.md#registry)
- **机制**：核心协议代码入口注释写明所落实的设计页与参考提交
- **反查**：理论或设计页修订时，按元数据与出处登记表列出全部受影响的派生对象逐一复核

## Signals

用于辅助判断整体趋势的代理信号均从事件存储与宿主会话日志确定性算出：

- **协调占用**：Firstmate 仅由跟进消息触发的回合占比
- **交回质量**：缺报率、阻塞率，以及待决项从打开到解决的耗时分布
- **纠正频次**：由 user 纠正产生的 Case 数量与复发率

信号用于辅助趋势判断，改进是否保留最终依据 Case 证据与 user 判断
