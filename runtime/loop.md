# Loop

## Steps

[进化的 Loop](../theory/evolution/index.md#loop)在 sayori 中分六步运转：

| 步骤 | 责任方 | 位置 | 要点 |
| --- | --- | --- | --- |
| 记录 | 任何节点，或 user 提出记 Case | 发生处工作区的事件存储 | 一次工具调用。机制提供缺报、长期未解待决项与意外 Effect 作为候选 |
| 整理 | 维护 runtime 的 Mate | 建设区的维护 Task | 攒够一批或到周期时按 [Revision](#revision) 定位缺口，写成修订提议并预先写下[检验问题](../theory/evolution/evaluation.md#question) |
| 决定 | user | 决定日志 | 一份提议一个决定，写明证据、改哪一层、怎么改与怎样算有效 |
| 修订 | 维护 Mate 或其派出的 Sailor | 缺口所在层的独立分支 | 理论按本仓规则修改，设计页经候审状态审定，实现完成边界验证 |
| 采用 | 维护者经 user 批准 | 唯一共享分发构建 | 合入主干并构建生效，发布说明引用对应 Case，工作区按需执行迁移并撤掉已接管的旧义务 |
| 检验 | 维护 Mate | Case 后续追加事件 | 对照原场景、相邻场景与正常行为，验证通过或记复发并关联原条 |

- 一圈处理这一圈暴露的明确缺口，不人为限定每圈只修一条，但每个改动各配独立检验问题。证据不足、需要继续观察的留到下一圈
- 消费工作区的 Firstmate 在回路中负责记 Case 与配合迁移检验，整理与修订由建设区负责，消费区不直接修改共享底座

## Case

Case 记在发生处工作区的事件存储，契约见[记录的 Contracts](records.md#contracts)：

- **事实**：预期、实际与证据入口分字段写，缺项明确留空
- **归因**：直接观察标为 Fact，原因假设标为 Inference，二者分开写
- **生命周期**：通过只追加事件按案例标识折叠，从未处理到已处理并标明处理提交，再到已验证或已复发

## Revision

按[进化的 Revision](../theory/evolution/index.md#revision)定位缺口，并区分设计层与工程层：

| 缺口 | 改法 |
| --- | --- |
| 理论 | 修改理论真源，再沿出处复核受影响的设计页与派生物 |
| 设计 | 修改协作层或工程层设计页，重大变更退回候审状态等 user 确认 |
| 派生 | 修改协作层实现的机制代码或外部化内容文件 |
| 取得 | 规则已存在，调整进入上下文的方式，例如说明文案、加载顺序或唤醒条件 |
| 工程 | 修改工程层的工作区基座规范或通用工程 Skill |
| 环境 | 只改该工作区自己的配置、路由或特有规则 |

- **退场**：新机制接管某项旧人工规则后，在采用回执中逐项写明被替代的旧句、仍保留的职责与回退条件，避免新旧义务长期双写
- **减法**：长期无 Case、删掉后行为不变的规则，按[检验的 Value](../theory/evolution/evaluation.md#value)删除

## Provenance

- **内容**：外部化内容文件与工程层规范在入口元数据中写明对应的理论页、设计页与参考提交
- **机制**：核心协议代码入口注释写明所落实的设计页与参考提交
- **反查**：理论或设计页修订时，按出处列出全部受影响的派生文件逐一复核

## Signals

用于辅助判断整体趋势的代理信号，均从事件存储与宿主会话日志确定性算出：

- **协调占用**：Firstmate 仅由跟进消息触发的回合占比
- **交回质量**：缺报率、阻塞率，以及待决项从打开到解决的耗时分布
- **纠正频次**：由 user 纠正产生的 Case 数量与复发率

信号只服务判断，改进是否值得保留以 Case 证据与 user 判断为准
