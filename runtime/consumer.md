# Consumer

## Distribution

协作层与工程层采用正式化的单一共享分发，全机只维护一套协作层入口与工程层入口：

- **协作层**：实现仓 `sayori.run` 以标准宿主扩展包与统一命令行入口 `sy` 共享安装，提供协作机制、外部化内容说明与只读视图
- **工程层**：实现仓 `sayori.dev` 提供统一消费的工作区基座规范与自包含的通用工程 Skill
- **发布**：对共享底座的改造在独立分支完成并经边界验证，由 user 批准后合入主干并统一切换生效，工作区根目录不存放重复的源码副本，也不以逐区版本锁阻碍日常启动

## Contract

消费工作区保持轻薄，只提供本工作区独有的最小契约，协议实现不写死消费方的目录结构：

| 项目 | 位置 | 内容 |
| --- | --- | --- |
| 运行目录 | 工作区专属数据目录 | 本工作区的事件存储、本地易失状态与受管会话目录 |
| 路由 | 工作区入口文档 | 遵守工程基座规范的薄入口，列出本区仓库、环境、知识入口与特有规则 |
| 专有 Skill | 工作区 Skill 目录 | 只服务本区业务的薄适配或专有 Skill，命名不与共享层冲突 |
| 工作材料 | 工作区自有组织 | Task 合同、设计依据、证据文档以及暴露给环境端口的工作树登记 |

协作协议与通用工程做法全机各只有一份，接入工作区时移除本地重复的协作 Skill

## Domain

- **隔离**：一个工作区是一个独立领域，拥有各自的职责树、Firstmate、事件存储、本地状态与视图。不同领域，例如个人建设区与公司业务区，互不共享节点、仓库与业务内容
- **回看**：默认单工作区零额外配置。仅建设区需要跨区只读回看消费区 Case 以推动[进化回路](loop.md)时，通过显式只读来源登记声明目标路径，绝不越界写入、不把外区节点纳入本区职责树，也不带入消费方业务内容

> 例：曾因登记文档将隔离工作区写成单一职责树的外区，导致本区不断衍生前置任务阻塞消费区验证。也曾因环境检查按仓库全局扫描，将外区二十六个工作树混入本区报告淹没唯一相关发现

## Border

一条规则放哪一层，依次问四个问题，第一个回答是的就是它的层：

1. 换一种 runtime 仍然成立的协作原则或主张吗？成立就进[理论](../theory/index.md)
2. 只关于 agent 之间怎样协作、通知、交接或记录吗？是就进[协作层](index.md)
3. 换一个工作区依然原样成立的工程做法或工作区基座规范吗？是就进[工程层](../dev/index.md)
4. 都不是，就留在工作区

第一问只收原则与主张。具体的工程做法即便换一种 runtime 也成立，仍归第三问，避免工程层被理论吞掉。协作层或工程层出现只对某一工作区成立的内容，按缺陷处理

| 协作层 | 工程层 | 工作区 |
| --- | --- | --- |
| 派活、交回、验收、结束与退站 | Git 卫生、提交、分支、变基与工作树规范 | 仓库拓扑、环境配置与产品业务知识 |
| 汇报、待决项、决定、批准、Effect 与 Case 记录 | 工作区基座结构、Issue 与 PR 通用写法、测试规范 | 本区标签、发布脚本与平台专有适配 |
| 唤醒、来源信封、意图标注、焦点、`/branch` 与视图 | 自包含的通用工程 Skill 与义务退场做法 | 只在本机或本业务环境成立的经验与薄 Skill |

> 例：任务交回后由谁核对属于协作层。已合入工作树的清退纪律与忽略文件规则换任何工作区都成立，属于工程层。公司平台的环境凭证与业务标签只在本区成立，留在工作区
